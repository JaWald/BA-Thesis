\chapter{Evaluation}
\label{sec:evaluation}
Chapter~\ref{ch:benchmarks} defined the benchmark design and introduced the four architectures under comparison, as well as the three scenarios. This chapter presents and interprets the measurements obtained from the benchmark runs. First, the setup and environment are documented. The subsequent sections then present the measurements of the three scenarios. A final discussion draws together the trends observed across all scenarios, followed by a discussion of the limitations of this evaluation.

% ── Methodology ──────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Methodology}
\label{sec:evaluation:methodology}
\paragraph{Hardware}
All benchmark runs were performed on a desktop machine equipped with an AMD~Ryzen~7~5800X processor and \qty{32}{\giga\byte} of DDR4-3200 memory. The processor provides eight physical cores, each exposing two hardware threads through \ac{SMT}. Its L1 data cache is \qty{32}{\kibi\byte} in size, 8-way set associative, and organized in \qty{64}{byte} cache lines. The processor further supports the AVX2 instruction-set extensions, which the vectorized code paths rely on.

\paragraph{Environment}
The benchmarks were run on Ubuntu~26.04~LTS with the \mbox{kernel~7.0.0-28-generic}. Performance Boost Overdrive and C-States were disabled in the BIOS, the former to prevent frequency boosting, the latter to keep the benchmark core from entering low-power idle states. The remaining modifications were made at runtime by a setup script. Core Performance Boost was disabled and the frequency of all cores was locked to \qty{3.6}{\giga\hertz}, thus eliminating another potential confounder. The \ac{SMT} sibling sharing the physical core with logical CPU~2 (logical CPU~10) was disabled, so that no tasks running on logical CPU~10 would consume resources of core~2, to which the benchmark was pinned via \texttt{taskset}.

\paragraph{Build/Compiler}
The benchmarks were compiled with the rustc~1.95.0 compiler. Rust supports compilation profiles, which let the programmer declaratively define a set of compilation options. For the benchmark program, the profile \texttt{o3} was defined, which inherits from the standard \texttt{release} profile, explicitly disables debug information, and sets the optimization level to \num{3}. Two further compiler flags were set in the execution scripts: {\texttt{-C~target-cpu=native}} and {\texttt{-C~link-arg=-fuse-ld=mold}}. The former targets the CPU and enables AVX2 (supported by the used processor), the latter selects the mold linker, a drop-in replacement that only reduces linking time while producing an equivalent executable~\cite{mold}. This choice therefore has no effect on the run time of the architectures.

\paragraph{Measurement Protocol}
To further diminish the impact of OS jitter, a setup with iterations and samples is used. In a given scenario, the four architectures perform a number of warmup runs, whose results are discarded, followed by a number of measured iterations. The warmup lets the caches reach a steady state before timing begins. The architectures are measured in the order of \ac{PC}, \ac{AoS}, \ac{SoA} and Bevy. This whole procedure is executed \texttt{samples} times.

As an example, consider the measurement parameters for Scenario~2 in Table~\ref{tab:methodology}. Instead of each architecture being measured in one block of \num{1000} iterations, the architectures are measured in interleaved, smaller blocks, namely \num{5} samples of \num{200} iterations in the case of Scenario~2. Thus, a larger system interrupt would be more likely to affect multiple or all architectures instead of only one. Each sample stores the run time over its \texttt{iterations} update steps as a single \texttt{time\_ns} value in the \ac{CSV}. The division by the iteration count, resulting in the time per iteration, as well as the averaging over the samples are performed when the plots are generated, which display the mean per-iteration time across all samples.

% ── Scenario 1 ───────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Scenario 1: Compute-Bound}
\label{sec:evaluation:scenario1}
Scenario~1 measures performance in the compute-bound case, where the arithmetic of the physical update (see \Cref{sec:benchmarks:simulation}) dominates the run time. The only swept parameter is the planet count, and since all architectures perform the identical update, any measured difference stems solely from the memory layout and the resulting code. 

% ── scaling ──────────────────────────────────────────────
\paragraph{Scaling Behavior}
Figure~\ref{fig:s1} plots the average per-iteration time in microseconds against the planet count in thousands, on linear axes and with one line per architecture. As is clearly visible, all four architectures scale linearly, yet with clear performance differences between them. The most performant one in calculating the positional update of \num{30000} planets is, with a big margin, the \ac{SoA} architecture, only taking \qty{22.62}{\micro\second} per iteration. In second place is the other data-oriented approach, the Bevy architecture, requiring \qty{106.34}{\micro\second} per iteration. Then follows the \ac{AoS} architecture with \qty{138.32}{\micro\second} and concluding with the \ac{PC} architecture with \qty{213.91}{\micro\second} per iteration.

\centering
\includegraphics[width=\linewidth]{images/S1.pdf}
\caption{Average time per iteration versus planet count}
\label{fig:s1}
\end{figure}

Note the wide yet relatively constant variation in measurements regarding the \ac{PC} architecture, which lessens after \num{16384} planets. Additionally, a number of spikes in execution time are visible in the measurements of the Bevy and \ac{SoA} architectures. However, these spikes do not affect the overall trend. 

% ── assembly ─────────────────────────────────────────────
\paragraph{Assembly Analysis}
To verify the results visible in Figure~\ref{fig:s1}, the assembly code of the \texttt{bench\_s1\_pc}, \texttt{bench\_s1\_aos}, \texttt{bench\_s1\_soa}, and \texttt{bench\_s1\_bevy} functions is inspected for the usage of the wider \texttt{ymm} registers and packed instructions. Note that the machine code can reach several hundred lines of code. Therefore, Listing~\ref{fig:s1:asm} mainly focuses on arithmetic of the hot loop, which is the calculation of acceleration and its application to velocity and position. The machine code instructions are reordered to match the source order. Regarding the \ac{SoA} architecture, for the per-component velocity and position update, only the x-component is shown.

vmulps    xmm7, xmm7, xmm5

Listing~\ref{fig:s1:asm} shows that the \ac{SoA} architecture is able to work with the wider \qty{256}{}bit \texttt{ymm} registers, while the \ac{AoS} architecture is forced to operate on the narrower \qty{128}{}bit \texttt{xmm} registers. Additionally, the \ac{SoA} architecture is able to vectorize, relying heavily on packed instructions such as \texttt{vmulps} and \texttt{vsqrtps}. Finally, the \texttt{add~rax,~8} advances the index by eight elements, so the next eight planets are processed. 

In contrast, the \ac{AoS} architecture cannot vectorize fully, falling back to scalar instructions such as \texttt{vdivss} and \texttt{sqrtss}. Additionally, the stride \texttt{add~rsi,~24} equals the size of the \texttt{PlanetAoS} struct in bytes, confirming that only one planet is processed per iteration rather than eight.

Regarding the low performance of the \ac{PC} architecture, the machine code shows that the arithmetic between the \ac{AoS} and \ac{PC} architectures is identical. As visible in Listing~\ref{fig:s1:asm:pc}, the main difference is how the planet's data is accessed, with \ac{AoS} able to load data directly and \ac{PC} having to fetch the data through the pointer address. This is further confirmed by the stride length of \num{24} for \ac{AoS}, which is the \texttt{PlanetAoS} struct's size in bytes, whereas the stride length for \ac{PC} is \num{8}, a pointer's size in bytes.

The Bevy architecture does not compile to a single, isolated hot loop, as the chunked entity iteration produces several separate loops. Therefore, no representative excerpt is shown. Its arithmetic is partially vectorized, as some \texttt{ymm} registers are present in comparison to the object-oriented architectures, which use only \texttt{xmm} registers. However, the usage of these \texttt{ymm} registers is interwoven with shuffle instructions, e.g., \texttt{vshufpd}, that assemble the lanes, i.e., the individual value slots within a vector register. This reflects only partial vectorization compared to \ac{SoA}, which in contrast can cleanly operate on eight planets at once. This is likely a consequence of the \texttt{Vec3A} layout, which stores each entity's x, y, and z coordinates together unlike the \ac{SoA} architecture. However, the usage of the \ac{ECS} still enables a considerable performance improvement compared to the object-oriented architectures, as it enables at least partial vectorization and usage of wider registers. 

% ── interpretation ───────────────────────────────────────
\paragraph{Interpretation}
To summarize, the memory layout dictates whether vectorization can occur or not. As was seen, the \ac{SoA} architecture was able to fully exploit the usage of wide registers and packed instructions due to the component arrays, whereas the object-oriented approaches employing interleaved memory layouts were not able to vectorize. Bevy lies in the middle, achieving partial vectorization. Additionally, the effect of memory locality was isolated between the \ac{AoS} and \ac{PC} architectures, demonstrating that vectorization is not the only aspect that can improve performance. To conclude, in a compute-bound scenario, the benefit of a data-oriented approach lies not in performing each calculation faster (the arithmetic is identical) but in how many planets are processed per instruction. The performance of Bevy shows that a practical, ECS-based approach can outperform the object-oriented layouts in this compute-bound case, though the necessity to use structs such as \texttt{Vec3A} impedes the full speed-up that a pure \ac{SoA} architecture would achieve. Thus, programs do not adhere exactly to either \ac{DOP} or \ac{OOP}, but lie on a spectrum spanned between the two.

\section{Scenario 2: Memory-Bound}
\label{sec:evaluation:scenario2}
In contrast to Scenario 1, which measured the performance difference when compute-bound, Scenario 2 measures the impact when the computational workload is negligible, but large amounts of data are accessed. As defined in \Cref{sec:benchmarks:scenario2}, the hot loop is reduced to a positional update based on existing velocity, with the payload size as the swept parameter. The decisive difference is that the object-oriented architectures carry the payload inline and must load it, whereas the \ac{SoA} and Bevy architectures keep it separate and skip it during the update. 

% ── scaling ──────────────────────────────────────────────
\paragraph{Scaling Behavior}
Figure~\ref{fig:s2} plots the average per-iteration time in microseconds against the payload size in KiB, on linear axes with one line per architecture. As was stated in Section~\ref{sec:background:ecs}, an \ac{ECS} benefits greatly from the separation of relevant and irrelevant data, which is exactly what these results show. While the execution time of the \ac{PC} and \ac{AoS} architectures increases with payload size, the \ac{SoA} and Bevy architectures remain constant. The order of performance is the same as in Scenario 1, with \ac{SoA} being the fastest with an average time per iteration across the sweep of \qty{2.32}{\micro\second}. In second is the Bevy architecture with \qty{5.03}{\micro\second}, followed by the \ac{AoS} architecture with \qty{26.69}{\micro\second} and the \ac{PC} architecture with \qty{37.94}{\micro\second}.

% ── analysis ─────────────────────────────────────────────
\paragraph{Cache Analysis}
The \texttt{PlanetAoS} struct possesses \qty{24}{\byte} of relevant data, i.e., \texttt{Vec3 velocity} and \texttt{Vec3 position}. Thus, the size of a planet in the object-oriented architectures is exactly these \qty{24}{\byte} plus the payload size, resulting in the aforementioned spikes being situated at \emph{exactly} multiples of \qty{1024}{\byte}. Additionally, zooming in reveals that these multiples form an upper bound, with each spike always being \qty{4}{\byte} in width, as is visible in Figure~\ref{fig:s2-spikes}. This occurs for all three spike categories: small, medium, and large. Within each category, lighter shades denote smaller and darker shades larger payload sizes.

\label{fig:s2-spikes}
\end{figure}

While the data-oriented architectures feature relatively constant values for \ac{CPI} and L1 cache miss rate with no clear pattern between the on-spike (\qtylist{998;2022;4070}{\byte}) and off-spike (\qtylist{1010;2034;4082}{\byte}) values, the opposite is true for the \ac{AoS} architecture. Here, the L1 cache miss rate clearly increases when execution time spikes, showing values of \qtylist{26.67;77.11;96.79}{\percent} respectively. Additionally, the \ac{CPI} increases significantly on spikes, with values of \numlist{1.474;6.426;12.680} respectively. For \ac{PC}, the miss rate and \ac{CPI} rise only gradually and shows no \mbox{on-/off-spike} difference. Its spikes are therefore not explained by this measurement and are likely shifted by the additional pointer indirection and allocator offsets.

While the values in Table~\ref{tab:s2:cache} indicate that the spikes occur due to a cache phenomenon, they do not fully explain \emph{what} cache phenomenon is to blame. To find the cause, the cache architecture was inspected. For these benchmarks, an \mbox{AMD Ryzen 7 5800x} was used, which features an 8-way set associative cache with a L1 data cache \qtylist{32768}{\byte} in size and \qty{64}{\byte} cache lines. The L1 cache is divided into \num{64} sets, following \qty{32768}{\byte} / (\num{8} ways × \qty{64}{\byte}) \cite{hennessy2011computer}. Each planet's data maps to one of these sets based on its address, the set being calculated by dividing the address by the \qty{64}{\byte} line size and taking the result modulo \num{64}.

Table~\ref{tab:s2:sets} lists this progression. When the struct size is a power of two, the planets fall into only a few sets, e.g., a struct size of \qty{4096}{\byte} maps every planet to the same set, \qty{2048}{\byte} to two sets, \qty{1024}{\byte} to four and so on. Each set holds only eight planets at once, since the cache is 8-way set associative. When more than eight planets map to the same set, each new one evicts an earlier planet, which must then be reloaded from memory on its next access. This repeated eviction and reloading is what raises the L1 miss rate seen in Table~\ref{tab:s2:cache} and produces the spikes in execution time. It also explains their hierarchy, as at a struct size of \qty{4096}{\byte} every planet lands in the same set, at \qty{2048}{\byte} every second planet, and at \qty{1024}{\byte} every fourth. The fewer sets involved, the more planets collide, which is why the \qty{4096}{\byte} spikes are the largest and the \qty{1024}{\byte} spikes the smallest.

% ── interpretation ───────────────────────────────────────
\paragraph{Interpretation}
In a memory-bound scenario the separation of relevant and irrelevant data decides the performance of an architecture. The \ac{SoA} and Bevy architectures hold the irrelevant data in separate arrays and components, resulting in constant execution times. In contrast, the object-oriented architectures hold the irrelevant data in the struct itself, polluting the cache and increasing execution times. The conflict-miss spikes are a structural artifact of this interleaved layout, which the data-oriented architectures cannot exhibit at all. While in Scenario 1 \ac{DOP} won by leveraging vectorization, it wins in this scenario through better cache efficiency. However, Bevy was able to close the gap to the \ac{SoA} architecture far better than in Scenario 1, as the usage of the \texttt{Query} mechanism omits the irrelevant data just as the \ac{SoA} architecture never touches its separate payload array. In conclusion, the performance is determined by the memory layout rather than by the computation itself.

\section{Scenario 3: Allocation and Deallocation}
\label{sec:evaluation:scenario3}
This scenario investigates the differences in performance regarding allocation and deallocation of data. Per iteration, \texttt{chunk\_size} planets are created and then removed, across a payload sweep, where the payload size influences the object size. To simulate both a particle system and a more complex simulation, two subscenarios are used, namely drop and reuse. In the drop case, the data is discarded once the planet is removed. In the reuse case, the popped value is passed to \texttt{black\_box}, which forces it to be materialized and thereby triggers a memcpy of the payload. 

The four architectures differ in how their data is allocated. The PC architecture stores each planet in a \texttt{Box<T>}, so every object requires an individual allocation and deallocation (\texttt{malloc} / \texttt{free}). The AoS and SoA architectures hold their planets directly in vectors and can therefore be allocated in bulk. The Bevy architecture uses its own ECS spawn / despawn logic.

Unlike the previous scenarios, no arithmetic is performed on the planets, as the timed region contains only the creation and removal of objects, isolating the cost of allocation and deallocation.

% ── scaling ──────────────────────────────────────────────
\paragraph{Scaling Behavior (Reuse)}
Figure~\ref{fig:s3-reuse} shows the performance in the reuse case on a logarithmic scale. As is visible, the Bevy architecture, in contrast to Scenarios 1 and 2, no longer beats the \ac{AoS} architecture. Its execution times start high with an iteration time of \qty{59.17}{\micro\second} with a payload of \qty{0}{\byte}, whereas the \ac{AoS} architecture is roughly ten times faster with \qty{5.95}{\micro\second}, closely followed by the \ac{SoA} architecture with \qty{6.06}{\micro\second}, which is followed by the \ac{PC} architecture with \qty{13.05}{\micro\second}. 

However, this order does not last beyond a payload of \qty{1000}{\byte}, as the \ac{SoA} architecture outperforms \ac{AoS} with increasing payload and the relative gap to the Bevy architecture decreases. At a payload of \qty{5}{\kilo\byte}, Bevy takes, on average, \qty{194.61}{\micro\second} per iteration, \ac{AoS} takes \qty{127.59}{\micro\second} and \ac{SoA} takes \qty{94.81}{\micro\second}. The \ac{PC} architecture's execution times rise steeply at a payload of roughly \qty{1000}{\byte} but then follow the same scaling as the other three architectures, resulting in an average iteration time of \qty{2641.33}{\micro\second} at a payload of \qty{5}{\kilo\byte}.

Lastly, while there are some variations in execution time in the vicinity of \qty{4}{\kilo\byte} and \qty{8}{\kilo\byte}, they do not undermine the trend or the ordering of architectures. However, below a payload of \qty{1000}{\byte}, the measurements for all architectures except Bevy overlap within the measurement noise and cannot be cleanly separated.

\begin{figure}[htbp]

\paragraph{Scaling Behavior (Drop)}
In contrast, the drop case does not feature the same variations in execution time at \qtylist{4;8}{\kilo\byte}. The \ac{SoA} architecture leads in performance, followed by the \ac{AoS} architecture and then Bevy. While the \ac{PC} architecture does not experience a stark difference in performance, the other three architectures' average execution times drop significantly. At a payload of \qty{5}{\kilo\byte}, the values for \ac{SoA}, \ac{AoS}, Bevy and \ac{PC} are \qtylist{34.80;69.21;120.13;2744.62}{\micro\second} respectively which are \qtylist{36.7;54.2;61.7;103.9}{\percent} of the execution times measured in the reuse case. Again, the \ac{PC} architecture shows a steep rise in execution times at roughly \qty{1}{\kilo\byte} payload size. 

% ── analysis ─────────────────────────────────────────────
\paragraph{Analysis (Reuse versus Drop)}
In the reuse case, the two bulk-storage architectures take substantially longer than in the drop case: the drop case completes in only \qtyrange{37}{62}{\percent} of the reuse time, while the \ac{PC} architecture is unaffected and stays within measurement noise. The cause is that \texttt{black\_box} forces the compiler to materialize the popped planet, which requires a \texttt{memcpy} the size of one planet (\qty{24}{\byte}~+~payload). In the drop case this copy is unnecessary, as the popped element is never read and the compiler only decrements the vector's length.

Listing~\ref{fig:s3:asm} shows the \ac{AoS} \texttt{pop} in both cases and the \ac{PC} \texttt{pop} in the reuse case, all with a payload of \qty{2}{\kilo\byte}. In the \ac{AoS} reuse case, the address of the popped element is first computed (lines~4--5) as its index times the object size of \qty{2024}{\byte}. Line~8, \texttt{call~r13}, is the decisive instruction: \texttt{r13} holds the address of \texttt{memcpy}, so the element is copied out in full. This call is not present in the drop case, where the popped element is never read and only the length is decremented (\texttt{dec~rax}). 

In the \ac{PC} reuse case, no payload \texttt{memcpy} occurs. Instead, only the \qty{8}{\byte} \texttt{Box} pointer is read from the vector (line~4) and materialized for \texttt{black\_box} (line~5). The \texttt{Box} is then freed via \texttt{call~\_\_rust\_dealloc} (line~8), which is present in the drop case as well and dominates the cost in both. Thus \ac{AoS} and \ac{SoA} (not shown) differ between reuse and drop essentially by one payload-sized \texttt{memcpy}, whereas for \ac{PC} only a pointer is copied and the allocation cost dominates.

\paragraph{Analysis (PC anomaly)}
Figure~\ref{fig:s3-reuse} and Figure~\ref{fig:s3-drop} both showed a steep rise in execution time of the \ac{PC} architecture at a payload of roughly \qty{1}{\kilo\byte}. Figure~\ref{fig:s3-tcache-on} shows that the cutoff is located at exactly \qty{1008}{\byte} of payload and is independent of the chunk size, which only scales the height of the slow region. An identical cutoff exists in the drop case (not pictured). At this cutoff payload, the object size is \qty{1008}{\byte} plus the \qty{24}{\byte} of fixed fields, i.e., exactly \qty{1032}{\byte}. As the cutoff is not gradual but sharp, it points to an allocator threshold that is exceeded above a struct size of \qty{1032}{\byte}. 

\begin{figure}[htbp]
\centering
\includegraphics[width=\linewidth]{images/S3_tcache_on.pdf}
\caption{Finer sweep at \qty{1}{\kilo\byte} of payload}
\label{fig:s3-tcache-on}
\end{figure}

\clearpage
This exactly matches the default value of the glibc tunable \texttt{tcache\_max}, which on 64-bit systems is \qty{1032}{\byte}~\cite{glibc_tunables}. This value is the largest object size that glibc still keeps in a small per-thread cache of recently freed blocks. Reusing a block from this cache is considerably faster than a full allocation, as it needs no coordination between threads~\cite{delorie_malloc_internals}. As long as an object is at most \qty{1032}{\byte} in size, i.e., for payloads up to \qty{1008}{\byte}, every creation and removal in the \ac{PC} architecture is handled by this fast cache. Once the object grows beyond \qty{1032}{\byte}, the cache no longer applies and each object must instead be requested from and returned to the general allocator, which is what produces the sharp rise in execution time.

To verify this, the fine sweep from Figure~\ref{fig:s3-tcache-on} was rerun with \texttt{GLIBC\_TUNABLES=glibc.malloc.tcache\_count=0}, which disables the per-thread cache~\cite{glibc_tunables}. Without the cache, the fast area below \qty{1008}{\byte} should disappear and the execution times should rise to the level otherwise seen only above the cutoff. Figure~\ref{fig:s3-tcache-off} confirms this: the sharp edge is gone, and the times below \qty{1008}{\byte} now match those measured above \qty{1008}{\byte} in the previous run.

\caption{Finer sweep at \qty{1}{\kilo\byte} of payload, without per-thread cache}
\label{fig:s3-tcache-off}
\end{figure}

\paragraph{Interpretation}
The deciding factor in Scenario 3 is the allocation strategy, namely whether objects are allocated individually or in bulk. The \ac{PC} architecture allocates and frees each planet separately and thus pays a per-object cost, whereas the \ac{AoS}, \ac{SoA} and Bevy architectures allocate in a contiguous buffer and avoid it. This is why \ac{PC} is an order of magnitude slower, while the differences among the bulk-allocating architectures stay small. Contrary to Scenarios 1 and 2, Bevy no longer outperforms the \ac{AoS} architecture, as without a compute or cache advantage the fixed overhead of its \ac{ECS} spawn and despawn functions dominate. The sharp cutoff for \ac{PC} follows from the per-object allocation, as only individual allocations hit the allocator's size threshold. To be noted is that the exact position at \qty{1032}{\byte} is specific to the glibc allocator, whereas the disadvantage of per-object over bulk allocation is general. Running this benchmark with another operating system, and thus likely a different allocator, may yield different results and different threshold effects. 

% ── Discussion ───────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Discussion}
\label{sec:evaluation:discussion}
The core message to be taken away from the results in the three Scenarios is that a memory layout outperforms the others due to different mechanisms, namely \ac{SIMD} vectorization, cache locality and allocation strategy. The \ac{SoA} architecture led throughout and \ac{PC} trailed in every scenario, while Bevy beat \ac{AoS} in Scenarios 1 and 2 through better vectorization and omitting irrelevant data, but lost in Scenario 3 once those advantages fell away and its \ac{ECS} overhead dominated.

As the four architectures demonstrate, a program rarely fully adheres to \ac{DOP} or \ac{OOP}, but finds itself on a spectrum between the two. The \ac{SoA} architecture, as the purest form of \ac{DOP}, led in performance but requires manually managing several separate vectors, a trade-off between performance and convenience that is a recurring theme in the \ac{DOP} literature~\cite{fabian2018data}. The object-oriented approaches keep each planet's data together, which is often more convenient to work with, but could not match \ac{SoA} in performance. Bevy may offer a middle ground, enabling some benefits of \ac{DOP} while keeping the code closer to an object-like structure. 

To conclude, choosing a memory layout should not be based solely on whether it is data-oriented or object-oriented, but on what best fits the requirements. Where performance is critical and the access pattern is regular, a \ac{SoA} architecture may be preferable, whereas where convenience and maintainability weigh more heavily, an object-oriented layout may be an acceptable trade-off.
% ── Limitations ──────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Limitations}
\label{sec:evaluation:limitations}
The results of this evaluation are, to a certain extent, dependent on the environment in which they were measured. As cache sizes and associativity were instrumental for the spikes in Scenario 2 and the register width in Scenario 1, the scaling behavior may differ on processors different to the \mbox{AMD Ryzen 7 5800X} (Zen~3), which was used for all benchmark runs in this thesis. Likewise, the benchmarks were compiled with a single \texttt{rustc} version and ran on Linux with the glibc allocator. The allocation threshold observed in Scenario 3 is a property of that specific allocator, and both vectorization and allocation may differ under another compiler, allocator, or operating system.

Regarding the benchmark design itself, the results should not be generalized without care. The workload is a synthetic micro-benchmark that attempted to isolate one bottleneck per scenario. While this approach makes the observed effects clearly visible, it does not reflect the complete behavior of real applications where all three effects and more occur together and may interact. Additionally, the payload used to control object size is likewise artificial and the Bevy \ac{ECS} used for the Bevy architecture represents only one framework rather than the \ac{ECS} approach in general. 

Finally, although measures were undertaken to reduce OS jitter via core pinning, a fixed clock and warmup runs, residual jitter remained visible occasionally, most noticeable in the results of the \ac{PC} architecture. Thus, the results are best read as trends and orders of magnitude and less as exact values.
