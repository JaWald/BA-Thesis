\chapter{Benchmark Design and Implementation}
\label{ch:benchmarks}
This chapter describes the benchmark program developed as part of this thesis, which is used to measure the performance of two object-oriented and two data-oriented architectures. First, it introduces the simulation on which all performance measurements are based. Then, the four architectures and the three scenarios in which they are measured are defined. The chapter concludes with the configuration and execution of an individual benchmark run.

% ── Simulation ───────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Simulation}
\label{sec:benchmarks:simulation}
To properly analyze the performance difference between \ac{DOP} and \ac{OOP}, the used simulation must be conceptually and mathematically identical across all evaluated architectures within a given scenario. Otherwise, differences in performance cannot be reliably attributed to the effects of adhering to one paradigm or the other, as they could just as likely occur due to inhomogeneous workloads. Additionally, the simulation must provide a workload that is non-trivial enough to cause the property under inspection to dominate the runtime, while still exercising that property. For example, a complex calculation may dominate the run time in a compute-bound scenario, yet it does not exercise the memory hierarchy sufficiently to expose the differences between memory layouts.

The benchmark simulation performs gravitational calculations on a certain number of planets. These planets always have the same three conceptual attributes, a 3D position in space, a 3D velocity, and a payload that acts as a way to artificially inflate the size of the planet objects. The position and velocity of all planets are randomly generated during the setup phase with a seeded random number generator, while the payload is a fixed size set at compile time. This design enables all three scenarios to operate on the same underlying simulation, with each of them varying a different parameter, e.g., planet count or payload size.

Following the laws of Newtonian gravitation~\cite{kleppner2014mechanics}, the simulation assumes that all planets are accelerated towards a central body of a large fixed mass (e.g., a black hole) at the origin. Due to the planets being accelerated towards this central mass, the planet's own mass cancels out, so the acceleration depends only on its position relative to that mass. The acceleration therefore simplifies to the following Equation,

$$\vec{a} = \frac{G}{r^2} \cdot \hat{d}$$

where $r$ is the distance between the planet and the center, and $\hat{d}$ is the unit vector pointing from the planet towards the center. Here, $G$ is not the physical gravitational constant but a fixed scaling factor that includes the constant central mass. Its value is derived from the gravitational constant $\qty{6.674e-11}{\newton\meter\squared\per\kilogram\squared}$ scaled by a factor of $10^{14}$, i.e., $G \approx \num{6674}$, so that the resulting accelerations remain in a numerically well-behaved range for 32-bit floating-point arithmetic. The planet's velocity and position are then integrated over a fixed time step $\Delta t$.

\section{Evaluated Architectures}
\label{sec:benchmarks:architectures}
Chapter~\ref{sec:background} contrasted \ac{OOP} and \ac{DOP} on the level of paradigms. However, a paradigm itself cannot be benchmarked. Concepts such as
encapsulation or a data-oriented mindset leave no direct trace in hardware. What reaches the hardware is the resulting arrangement of data in memory and the
pattern in which that data is accessed, which can then be measured. Thus, the comparison is reduced to representative implementations that differ precisely in these two properties. Since the simulated workload itself is identical across all of them (see Section~\ref{sec:benchmarks:simulation}), any measured difference can be attributed to the memory layout rather than to the workload. In total, four architectures are evaluated, two of which represent \ac{OOP} and two of which represent \ac{DOP} design principles. They are arranged such that each of them differs from the preceding one in primarily one property, namely memory layout, grouping of fields and usage of a higher-level \ac{ECS}. Thus, this arrangement spans a range from maximum indirection to maximum contiguity. 

\paragraph{(1) \ac{PC}}
The PC architecture stores planets as \texttt{Vec<Box<PlanetAoS>>}, where \texttt{PlanetAoS} has three fields: a \texttt{Vec3} for the planet's velocity, another \texttt{Vec3} for its position, and an array \mbox{\texttt{[u8;~PAYLOAD\_SIZE]}} for the payload. Every planet is allocated individually on the heap, with the vector solely holding the pointers to said planets. In Rust, this indirection is provided by \texttt{Box<T>}, where the content of the box lives on the heap and the box itself is a pointer of known size referring to the content \cite{klabnik2023rust}. This architecture represents the reference semantics of common object-oriented languages such as Java or C\#, where objects are allocated individually and accessed through references.

Since caches exploit spatial locality \cite{drepper2007every}, this layout is the least favorable one under inspection, as traversing the collection means following a pointer per element instead of having the data be laid out in a contiguous manner. This traversal pattern is commonly referred to as pointer chasing with Drepper \cite{drepper2007every} using it to demonstrate the limits of hardware prefetching. However, when objects are created within a single uninterrupted loop, a general-purpose allocator may place them in near-contiguous memory, in which case the architecture would degenerate into the \ac{AoS} architecture described below. To prevent this and ensure the layout causes pointer chasing, the vector is shuffled once after setup. This mirrors a long-living application under manual memory management, such as in C++, whose heap becomes fragmented as objects are allocated and freed over time. Managed languages with compacting garbage collectors, such as Java or C\#, relocate live objects and thus reduce such fragmentation, so the shuffled layout represents the worst case for those runtimes rather than their typical state.

\paragraph{(2) Array of Structures}
The \ac{AoS} architecture stores the identical \texttt{PlanetAoS} struct in a \texttt{Vec<PlanetAoS>}, i.e., without any indirection. The planets are laid out contiguously within the vector, whereas the fields of the planets remain interleaved, as illustrated in Figure~\ref{fig:background:memory-layout}. The position, velocity and payload of one planet are stored adjacently, followed by the fields of the next planet.

Within the object-oriented paradigm, this architecture therefore represents the
most contiguous layout achievable. The indirection present in the \ac{PC} architecture is removed while retaining the conceptual properties of an object, namely that all of its data is kept together. As the \ac{AoS} and \ac{PC} architectures share the exact same \texttt{PlanetAoS} struct and differ solely in the presence of a \texttt{Box<T>}, any measured difference can be directly attributed to the indirection alone.

\paragraph{(3) Structure of Arrays}
The \ac{SoA} architecture, in contrast to the previous two, adheres to \ac{DOP} principles. Instead of one vector holding whole planets, one vector is created per individual field. This results in three vectors for the x, y, and z coordinates of a planet's position, three vectors for the x, y, and z values of a planet's velocity and a vector holding the payload. Thus, a planet is no longer a singular entity with inhomogeneous data, but an index shared across seven homogeneous vectors.

This is the layout as described in Section~\ref{sec:background:dop} and represents the data-oriented ideal. It is implemented manually without any framework, so that it serves as the performance baseline against which any abstraction built on top of a \ac{SoA} layout is measured. Any performance costs incurred by abstraction built on top of a \ac{SoA} layout are measured relative to this baseline. However, manually managing and synchronizing seven parallel vectors is error-prone and cumbersome and does not reflect how data-oriented code is written in practice. There, such layouts are typically managed by a framework rather than by hand. This motivates the fourth architecture, which uses the Bevy ECS framework.

\paragraph{(4) Bevy ECS}
The Bevy architecture represents the same idea as the \ac{SoA} architecture, but implemented with an ECS framework. Bevy groups entities, in this case planets, by archetypes, i.e., by their exact set of components \cite{redmond2025ecs}, and stores the components of an archetype in contiguous, per-component storages \cite{bevy_storage}. Since all planets in this simulation possess an identical combination of components (\texttt{Position}, \texttt{Velocity}, \texttt{Payload}), they occupy the same archetype and the resulting storage pattern is thus conceptually equivalent to that of the \ac{SoA} architecture.

Therefore, the difference to the \ac{SoA} architecture is not how the data is stored, but the abstraction required to keep such a data-oriented layout maintainable. This includes entity identifiers, archetype metadata, and especially the query mechanism through which components are accessed. The idiomatic query iterator yields only one entity's components at a time, which could hinder vectorization. Thus, \texttt{contiguous\_iter\_mut} is used instead of \texttt{iter\_mut}, as it returns slices of homogeneous component blocks on which the compiler may perform vectorization. A benchmark accompanying the feature confirms this. The idiomatic iteration shows no AVX2 speed up, whereas contiguous slices do~\cite{bevy_contiguous}. As it is not yet part of a released engine version, the function is taken from an in-development build~\cite{bevy_contiguous}.

Therefore, Bevy represents \ac{DOP} as it is realistically adopted and the comparison with the \ac{SoA} architecture quantifies how much that convenience costs.

\paragraph{Vector Types and Comparability}
These four architectures do not only differ in memory layout, but also in their representation of position and velocity. While \ac{PC} and \ac{AoS} store them as \texttt{Vec3}, i.e., three consecutive \texttt{f32} values, the \ac{SoA} architecture stores the individual coordinates in separate vectors of \texttt{f32}. The Bevy architecture uses \texttt{Vec3A}, which extends the three \texttt{f32} values by \qty{4}{\byte} of padding and is aligned to a 16-byte boundary \cite{glam_vec3a}. A single position or velocity value therefore occupies \qty{16}{\byte} instead of the \qty{12}{\byte} occupied by the three coordinates in the remaining architectures. This is a deliberate decision, as each architecture uses the representation that is idiomatic for it. The measurements thus reflect the performance of code as it would be written in practice, instead of code that has been homogenized for the sake of uniformity.

Enforcing a single representation would distort the comparison in one direction or the other. Forcing Bevy to use \texttt{Vec3} would deny it the aligned accesses that vectorized instructions rely on, since 16-byte memory accesses are expected to be 16-byte aligned and the instruction variants handling unaligned accesses are slower \cite{drepper2007every}. Conversely, forcing \texttt{Vec3A} onto the \ac{PC} and \ac{AoS} structs would pad them and therefore inflate the memory footprint the comparison measures. This does not apply to \ac{SoA}, which stores the coordinates as raw \texttt{f32} and thus has no vector type to align in the first place.

The consequence of this decision is that the amount of hot data per planet is not identical across all architectures. Except for Bevy, which carries \qty{32}{\byte} of position and velocity per planet, all architectures carry \qty{24}{\byte}. Bevy therefore trades a larger data footprint for the alignment its layout exploits. The payload, in contrast, is identical across all architectures and, when varied, is varied for all four simultaneously. This is relevant as it is one of the parameters varied in Scenarios~2 and~3.

% ── Scenario 1 ───────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Scenario 1: Compute-Bound}
\label{sec:benchmarks:scenario1}
The first scenario aims to answer the question of how well the compiler can vectorize the per-planet update and how large the resulting performance difference is, depending on the architectures under inspection. Additionally, the results should show whether a \ac{SoA} layout is a precondition for effective \ac{SIMD} vectorization as has been previously stated in Section~\ref{sec:background:simd}. In order to achieve this, this scenario features the entire calculation of gravitational pull (see Section \ref{sec:benchmarks:simulation}) and sets the payload size deliberately to \qty{0}{\byte}. Otherwise, the memory overhead could distort the results and would not allow proper conclusions from the measurements.

\paragraph{Parametrization}
In this scenario, the number of planets is the only parameter being varied. It is swept from \num{1} planet up to \num{30000}, while the payload remains fixed at \qty{0}{\byte} and the number of warmup and measurement iterations as well as the number of samples, i.e., repeated measurements, remain constant. Varying solely the planet count enables one to isolate the performance impact of scaling the arithmetic workload linearly, as the memory layout and footprint of a single planet remain identical throughout the sweep. Any difference between the architectures can therefore be attributed to how efficiently each of them executes the same arithmetic. Lastly, the sweep is performed in fine-grained steps rather than in orders of magnitude. This is deliberate, as this approach causes threshold effects to remain visible instead of being averaged away between two distant measurements.

\paragraph{Update Logic}
The gravitational equation is translated directly into code. For every planet, the direction vector towards the center is obtained by negating the planet's position, from which the squared distance follows. The acceleration is then applied along the normalized direction. Lastly, velocity and position are updated over the fixed time step \texttt{dt}. Listing~\ref{lst:s1aos} shows the hot loop body being measured for the \ac{AoS} and \ac{PC} architectures. The sole difference between the two is the usage of \texttt{Box<T>} in the \ac{PC} architecture, which enables the isolation of the effect of the usage of pointers versus direct memory access. 

\begin{lstlisting}[language=C++, caption={Update loop of the AoS and PC architectures}, label={lst:s1aos}]
for planet in planets.iter_mut() {
    // calculates acceleration
    let direction = -planet.position;
    let r_squared = direction.length_squared();
    let a_scalar = G / r_squared;
    let a = a_scalar * direction.normalize();

    // updates velocity and position
    planet.velocity += a * dt;
    planet.position += planet.velocity * dt;
}
\end{lstlisting}

While there is a data dependency between the velocity and position of a planet, i.e., the velocity must be written before position can read it, it is not in the way of vectorization as it is contained within a planet. Whether \ac{SIMD} vectorization occurs therefore depends on the respective memory layout. 

\clearpage
\begin{lstlisting}[language=C++, caption={Update loop of the SoA architecture}, label={lst:s1soa}]
for i in 0..planets.positions_x.len() {
    let px = planets.positions_x[i];
    let py = planets.positions_y[i];
    let pz = planets.positions_z[i];
    // calculates acceleration
    let r_sq = px * px + py * py + pz * pz;
    let r_recip = 1.0 / r_sq.sqrt();
    let a_scalar = G / r_sq;
    let nx = -px * r_recip;
    let ny = -py * r_recip;
    let nz = -pz * r_recip;
    // updates velocity and position
    planets.velocities_x[i] += nx * a_scalar * dt;
    planets.velocities_y[i] += ny * a_scalar * dt;
    planets.velocities_z[i] += nz * a_scalar * dt;
    planets.positions_x[i] += planets.velocities_x[i] * dt;
    planets.positions_y[i] += planets.velocities_y[i] * dt;
    planets.positions_z[i] += planets.velocities_z[i] * dt;
}
\end{lstlisting}

The \ac{SoA} implementation performs the same computation, but on six of the seven vectors from Section~\ref{sec:benchmarks:architectures}, as the payload remains untouched. The difference to \ac{AoS} and \ac{PC} is therefore not what is computed, but which values lie adjacent in memory. There, the three coordinates of a single vector are adjacent and consecutive planets are separated by the stride of the entire struct. Here, the x, y, and z values of consecutive planets are adjacent and thus form homogeneous data streams that can be vectorized, at the cost of markedly higher code complexity. To keep the arithmetic identical across architectures, \texttt{normalize()} is mirrored through \texttt{r\_recip}, as it is internally implemented as a multiplication by the reciprocal of the length rather than as three separate divisions.

\begin{lstlisting}[language=C++, caption={Update loop of the Bevy architecture with contiguous component slices}, label={lst:s1bevy}]
for (mut pos_slice, mut vel_slice) in query.contiguous_iter_mut(&mut world).unwrap() {
    for (pos, vel) in pos_slice.iter_mut().zip(vel_slice.iter_mut()) {
        // calculates acceleration
        let direction = -pos.0;   // unwraps the Position component to its inner Vec3A
        let r_squared = direction.length_squared();
        let a_scalar = G / r_squared;
        let a = a_scalar * direction.normalize();
        // updates velocity and position
        vel.0 += a * dt;
        pos.0 += vel.0 * dt;
    }
}
\end{lstlisting}

Finally, the Bevy architecture performs the same arithmetic and differs only in how the components are reached. As described in Section~\ref{sec:benchmarks:architectures}, \texttt{contiguous\_iter\_mut} yields slices rather than individual entities, over which the inner loop then iterates directly. Here, the trade-off again is between performance and code-complexity. Unlike the \ac{SoA} architecture however, Bevy may occupy what could best be called a middle ground.

\paragraph{Verification}
While substantially better performance of the \ac{DOP}-based architectures would suggest that vectorization has taken place, it would not by itself prove it. The generated x86-64 assembly is therefore inspected to determine whether the compiler emitted scalar instructions (\texttt{vaddss}, \texttt{vmulss}) or their packed \ac{SIMD} counterparts (\texttt{vaddps}, \texttt{vmulps}), and whether 128-bit \texttt{xmm} or 256-bit \texttt{ymm} registers are used, with examples being present within the analysis in Section~\ref{sec:evaluation:scenario1}. The inspection uses \texttt{cargo-show-asm} \cite{cargo_show_asm}, which interleaves assembly with the corresponding Rust source lines, and IDA Free \cite{ida_free}, whose control flow representation makes the hot loop easier to identify. Vectorization can only occur if the compiler is permitted to emit the required instruction set extensions, enabled here by compiling with \mbox{\texttt{-C~target-cpu=native}} (further build details in Section~\ref{sec:evaluation:methodology}).
    
% ── Scenario 2 ───────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Scenario 2: Memory-Bound}
\label{sec:benchmarks:scenario2}
As has been established in Section~\ref{sec:background:dop}, cache pollution is the phenomenon when an object's data fills the CPU cache with data that is not relevant to the operation. In this scenario, this additional yet irrelevant data is simulated by the payload field of the planet structs, which is never read and serves solely to increase the size of a planet. The goal is to measure how strongly this unused data affects execution time, and from which object size onwards it begins to do so. As the intent is to have this scenario memory-bound, the calculation of gravitational pull is reduced to the update of a planet's position based on its current velocity, so as not to distort the results of benchmark runs with little payload. Conceptually, the planets do not rotate around a large mass anymore but wander through space in straight lines. Scenario 1 and Scenario 2 are thus complementary: the former minimizes the payload to measure the arithmetic, while the latter minimizes the arithmetic to measure the memory footprint's impact. 

\paragraph{Parametrization}
In contrast to Scenario 1, the planet count remains fixed at \num{10000}, while the payload is the only parameter being varied, sweeping from \qty{0}{\byte} up to \qty{20000}{\byte}. The number of warmup and measurement iterations as well as the samples per invocation again remain constant. The payload is deliberately declared as an array of fixed length rather than as a heap-allocated vector, so that it is stored within the struct itself and thus actually increases the size of a planet. In contrast, a vector would merely add a small, fixed-size handle to the structs size and thus leave the struct small. As the array's length is part of its type and thus must be known at compile-time, it requires a re-compilation for every payload size (see Section~\ref{sec:benchmarks:execution}). The sweep is again performed in fine-grained steps, as the effects of cache conflict misses (see Section ~\ref{sec:background:cache}) are expected to appear at specific object sizes rather than gradually, and would be averaged away between two distant measurements.

\paragraph{Update Logic}
The core difference between architectures is now not directly visible in code anymore, as the differences are located in the underlying memory layout. For the \ac{PC} and \ac{AoS} architectures, the payload is interleaved with the position and velocity within each planet struct. Since the cache operates on fixed-size cache lines, every line fetched for the position and velocity also pulls in adjacent payload bytes, wasting precious cache bandwidth on irrelevant data. When performing an operation solely on the position and velocity vectors, only these relevant vectors may be loaded with the payload remaining untouched. Thus, the cache is filled only with relevant data, leading to potentially substantial performance improvements.

\begin{lstlisting}[language=C++, caption={Update loop of all four architectures in Scenario 2}, label={lst:s2}]
// PC and AoS
for planet in planets.iter_mut() {
    planet.position += planet.velocity * dt;
}
// SoA
for i in 0..planets.positions_x.len() {
    planets.positions_x[i] += planets.velocities_x[i] * dt;
    planets.positions_y[i] += planets.velocities_y[i] * dt;
    planets.positions_z[i] += planets.velocities_z[i] * dt;
}
// Bevy
for (mut pos_arr, mut vel_arr) in query.contiguous_iter_mut(&mut world).unwrap() {
    for (pos, vel) in pos_arr.iter_mut().zip(vel_arr.iter_mut()) {
        pos.0 += vel.0 * dt;
    }
}
\end{lstlisting}

Listing~\ref{lst:s2} shows the reduced complexity of the update loop of all four architectures. The \ac{SoA} architecture uses a \texttt{PlanetsSoA} struct which contains seven vectors, six of which represent the x, y and z values of position and velocity of all planets, with the seventh containing the payload of all planets. As the payload is not required for the update on position, the array is simply not accessed and the cache is thus kept full with the relevant coordinate data. The Bevy architecture follows the same principle, querying only for the position and velocity components and never accessing the payload component. Bevy's idiomatic iterator (\texttt{query.iter\_mut}) closely resembles the \ac{OOP} update loop and would offer comparable syntactic simplicity. Here, however, the \texttt{contiguous\_iter\_mut} variant is used instead, as only \texttt{contiguous\_iter\_mut} exposes it as \texttt{\&mut [T]} slices. This slice-based access allows the compiler to vectorize the loop and thus increases comparability between the Bevy and \ac{SoA} architectures, at the cost of a more complex and verbose nested loop.

\paragraph{Verification}
While again the assembly code is inspected to verify the existence of vectorization, the main focus now lies on the cache miss rate, which is gathered with AMD~µProf~\cite{amd_uprof}. A high cache miss rate would clearly indicate the cache being filled with irrelevant data, as a large payload size in relation to the relevant data leads to substantially more cache misses. As the effect of cache inefficiencies and cache conflict misses is highly dependent on the exact payload size used and different payload sizes necessitate separate binaries, it is not feasible to inspect every single binary created. Instead, the binaries at and around strong variations in performance are evaluated for \ac{SIMD} instructions and cache miss rate to confirm the variations occur due to the aforementioned reasons. 

% ── Scenario 3 ───────────────────────────────────────────────────────────────────────────────────────────────────────
\section{Scenario 3: Allocation and Deallocation}
\label{sec:benchmarks:scenario3}
With Scenario 1 measuring the cost of arithmetic and Scenario 2 the cost of a growing memory footprint, Scenario 3 measures the cost of repeatedly allocating and deallocating that data. This scenario simulates the repeated creation and destruction of planets. Practical implementations of this principle can be found with particle systems and projectiles in video games or short living entities in simulations. The core question is how expensive this repeated creation and destruction is, and how it scales with payload size and chunk size. Here, the chunk size declares how many planets are created and destroyed within a single iteration. As the focus is on memory management, the arithmetic in the update loop is left out completely. Additionally, two subvariants of this scenario are inspected, namely by how much performance differs depending on whether the data of destroyed planets is used after destruction or whether it is discarded.

\paragraph{Parametrization}
This scenario, contrary to Scenarios 1 and 2, involves two parameters: payload size and chunk size. For the main sweep, the chunk size is fixed at \num{500} while the payload is swept from \qty{0}{\byte} to \qty{10000}{\byte} in fine-grained \qty{2}{\byte} steps, as the scaling behavior is the main property under inspection. To generate the heatmaps in Section~\ref{sec:evaluation:scenario3}, chunk size is swept from 1 to 1000 in steps of 20 and payload size is swept from \qty{980}{\byte} to \qty{1035}{\byte}. As with Scenario 2, every change in payload requires re-compilation.

\paragraph{Update Logic}
As was previously stated, a distinction is made between discarding the popped objects and using their data. The discarding of data best represents conventional particle systems where particles are created, worked with and then destroyed. The reuse of data better represents entities in more complex simulations, where the data may needs to be read after destruction. Listing~\ref{lst:s3aos} shows this difference in code, where in the reuse case the \texttt{planets.pop()} function is surrounded by a \texttt{black\_box}, which in this case simulates the usage of the planet's data. On the contrary, \texttt{let \_ = planets.pop();} discards the data immediately, simulating a particle system. This distinction and the usage of \texttt{black\_box} occurs analogously in the \ac{SoA} and Bevy architectures. For the creation of the planets, the coordinates are filled with \num{0}.

\begin{lstlisting}[language=C++, caption={Deallocation of planets in \ac{PC} and \ac{AoS} architectures}, label={lst:s3aos}]
if reuse {
    for _ in 0..chunk_size { 
        black_box(planets.pop()); 
    }
} else {
    for _ in 0..chunk_size { 
        let _ = planets.pop(); 
    }
}
\end{lstlisting}

In the reuse case, the \ac{PC} and \ac{AoS} architectures differ notably. Popping a planet from the \ac{AoS} vector moves the whole struct out of storage, i.e., an implicit \texttt{memcpy} of the \qty{24}{bytes} of coordinates plus the full payload, so its cost grows with the payload size. In the \ac{PC} architecture, the same pop moves only the \qty{8}{byte} \texttt{Box} pointer while the data stays on the heap, making the cost payload-independent. This only shows in the reuse case, as \texttt{black\_box} forces the popped value to materialize; in the discard case the compiler is free to optimize the move away. This advantage is offset by allocation cost. In the \ac{PC} architecture, every \texttt{push()} triggers a \texttt{malloc} and every \texttt{pop()} a \texttt{free}, for each element in every cycle. The \ac{AoS} vector instead keeps its capacity across the cycles and thus barely allocates once it has grown. Therefore, \ac{PC} trades a cheap pop against constant \texttt{malloc} and \texttt{free} overhead, and which effect dominates is expected to depend on payload and chunk size.

The difference between the \ac{AoS} and \ac{SoA} architectures lies in the \ac{AoS} architecture requiring only a single \texttt{push()} and \texttt{pop()} per planet, whereas the \ac{SoA} architecture requires seven such calls due to the split management of values across seven vectors. Bevy provides its own \texttt{spawn()} and \texttt{despawn()} functions; in the reuse case, however, explicit calls to \texttt{get::<Position>()}, \texttt{get::<Velocity>()} and \texttt{get::<Payload>()} are necessary, as \texttt{despawn()} does not return the component data of the removed entity.

\paragraph{Verification}
To verify the results, the assembly code is inspected to confirm that allocations and deallocations have been carried out as intended and have not been optimized away by the compiler. For this, \texttt{cargo show-asm} \cite{cargo_show_asm} is used. Additionally, the usage of the \texttt{memcpy} instruction is inspected in the \ac{AoS} architecture, to confirm the hypothesis of it requiring expensive memory movements instead of simple pointer popping. A heatmap is used to visualize the runtimes and more easily discern if any threshold effects or performance anomalies occur.

An individual benchmark run is configured almost entirely through \ac{CLI} arguments, with the parsing of the commands being handled by the \texttt{clap} crate \cite{clap}. The program itself does not contain the functionality of parameter sweeping, i.e., varying parameter values within defined ranges. Instead, PowerShell and bash scripts are provided which repeatedly execute the benchmark with varying values. This keeps the measured code free from any sweeping logic and makes every measurement reproducible from its arguments alone. In addition, the scripts recompile the benchmarks with varying payload sizes for Scenarios 2 and 3, as the payload size is a compile-time constant and thus must be defined before the execution of the benchmarks. 

A single invocation executes all four architectures in sequence. For every architecture and for every sample, the corresponding benchmark function is called twice: once with the number of warmup iterations and once with the number of benchmark iterations. Calling the same function for both warmup and benchmark iterations ensures that the cache is in a comparable state when the measurements begin. A typical invocation is shown in Listing~\ref{lst:invocation}.

\begin{lstlisting}[frame=none, numbers=none, basicstyle=\ttfamily, keywordstyle={}, commentstyle={}, stringstyle={}, caption={A benchmark invocation for Scenario 3 via the command line}, label={lst:invocation}]
    cargo run --profile o3 -- -b s3 -w 1000 -i 5000 -s 5 -c 500 -r -d
\end{lstlisting}

Measurement results are appended to a \ac{CSV} file per architecture and scenario. For example, the above invocation would append the measurements to the files \texttt{bevy.csv, soa.csv, etc.} located at \texttt{../Benchmarks/diagrams/s3/csv/}. Each line contains an entry for the respective architecture, planet count, number of iterations, chunk size, reuse of deallocated data in Scenario 3, payload size in bytes as well as the elapsed time in nanoseconds. In order to delete the generated \ac{CSV} files, the \texttt{reset} value for the \texttt{benchmark} argument may be used. This acts as a way to create a clean slate and prevent appending measurements to those of previous benchmarks, should the \ac{CSV} files not have been moved yet.
